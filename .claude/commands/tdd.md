# TDD開発サイクル

**引数**: $ARGUMENTS (オプション: 作業対象の説明)

## 実行フロー

### Phase 1: 初期設計対話 (初回のみ)
README.mdとDESIGN.mdが存在しない場合、以下を実行:

1. **要件ヒアリング**
   - ユーザーと対話しながら要件を明確化
   - 曖昧な点、不明な点を積極的に質問
   - 技術選択、制約条件、想定ユーザーを確認

2. **設計文書作成**
   - README.md: プロジェクト概要、使用方法、要件
   - DESIGN.md: アーキテクチャ、設計判断、技術的詳細
   - 実装に値するレベルまで詳細化

3. **実装開始確認**
   「設計が十分に詳細化されました。実装を開始しますか？」

### Phase 2: TDDサイクル実行

#### Step 1: 現在状況の把握
```
状況確認:
- README.md, DESIGN.md の内容確認
- TODO.md の確認 (特に "In Progress" セクション)
- 進行中のタスクがある場合: そのフェーズから継続
- 進行中のタスクがない場合: 新しいサイクルを開始
- 直近のcommitログ確認 (git log --oneline -5)
```

#### Step 2: TODO決定・分解
```
作業対象の決定:
- $ARGUMENTS が指定されている場合: それをベースに作業
- 指定されていない場合: TODO.mdの "Next" から選択
- 選択したタスクを適切な粒度に分解
- 必要に応じて新しいTODOを追加・分割

TODO.md更新:
## In Progress
- [🔴 RED] [選択したTODO] - 失敗テスト作成中
  - Started: [現在時刻]
  - Goal: [このTODOで達成したいこと]

## Next
- [ ] [未着手のタスク1]
- [ ] [未着手のタスク2]

## Done
- [✅] [完了済みタスク] ([完了日時])
```

#### Step 3: Red - 失敗テスト作成
```
1. 設計文書を参照して期待動作を明確化
2. そのTODOを検証する最小限のテストを作成
3. テストを実行して意図的に失敗させる
4. コミット: "Red: Add failing test for [TODO内容]"

TODO.md更新:
- [🟢 GREEN] [TODO内容] - 実装中
  - Started: [開始時刻]
  - Goal: [目標]
  - Red completed: [時刻]
```

#### Step 4: Green - 最小実装
```
1. テストを通すための最小限の実装を作成
2. テストが通ることを確認
3. 他のテストが破綻していないことを確認
4. コミット: "Green: Implement [TODO内容]"

注意:
- Green フェーズでは「読みやすさ」「将来の拡張性」は考えない
- 目的は「事実（テストが通る実装）を作ること」だけ


TODO.md更新:
- [🔄 REFACTOR] [TODO内容] - リファクタリング中
  - Started: [開始時刻]
  - Goal: [目標]
  - Red completed: [時刻]
  - Green completed: [時刻]
```

#### Step 5: Refactor - 構造改善のみ
Refactor 進入条件（すべて満たすこと）:
- すべてのテストがグリーン
- 次に追加したい仕様・条件分岐が頭に浮かんでいない
- テストコードを一切変更せずに完結できる
- この変更を1コミットで元に戻せる自信がある

Refactor の定義:
- 外部から観測可能な振る舞いを一切変更しない
- テストコードは変更しない（追加・修正・削除すべて禁止）
- 新しい条件分岐・仕様・例外処理を追加しない

実行内容:
1. コードの読みづらさ・重複・責務の混在を特定
2. 小さな構造変更を1つずつ実施
3. 各変更後に必ずテストを実行
4. すべてのテストがグリーンであることを確認

禁止事項:
- 新しい振る舞いの追加
- 仕様解釈の変更
- パフォーマンス最適化目的のアルゴリズム変更

判断ルール:
- Refactor 中に「この振る舞いも必要では？」と感じた場合、
  その作業は直ちに中断し、新しい TODO として Red に戻る


コミット:
"Refactor: Improve internal structure of [対象範囲]"

TODO.md更新:
- [📝 FEEDBACK] [TODO内容] - 設計フィードバック中
  - Started: [開始時刻]
  - Goal: [目標]
  - Red completed: [時刻]
  - Green completed: [時刻]
  - Refactor completed: [時刻]
```

#### Step 6: 設計フィードバック
```
実装中に得られた洞察をチェック:
- README.mdの更新が必要か？
- DESIGN.mdの設計判断に変更が必要か？
- 新たに発見したTODOがあるか？

必要に応じて文書を更新しコミット:
"Docs: Update design based on implementation insights"

新しいTODOがあれば TODO.md の "Next" セクションに追加
```

#### Step 7: サイクル完了
```
TODO.md更新:
## In Progress
(空にする)

## Next
- [ ] [次のタスク1]
- [ ] [次のタスク2]

## Done
- [✅] [完了したTODO内容] ([完了日時])
  - Red/Green/Refactor/Feedback 全段階完了

サイクル完了を報告:
「TDDサイクル完了: [完了したTODO内容] 」
「次のTODO候補: [次に着手予定のタスク] 」
「継続する場合は再度 /tdd を実行してください」
```

## 重要な原則

**必須事項:**
- 各段階でREADME.md, DESIGN.mdを参照
- TODO.mdで現在の状態を明確に表現
- Red-Green-Refactorの各段階で必ずコミット
- 実装中の洞察を設計文書にフィードバック

**状態管理:**
- TODO.mdの "In Progress" セクションで現在フェーズを追跡
- フェーズアイコン: 🔴(RED) → 🟢(GREEN) → 🔄(REFACTOR) → 📝(FEEDBACK)
- 中断からの復帰時は "In Progress" を確認してそのフェーズから継続

**実行時の注意:**
- TODO.mdのみを状態管理に使用 (他のファイル追加禁止)
- テストファイルの命名規則はプロジェクトの既存パターンに従う
- コミットメッセージは簡潔で意図が明確なものにする
- リファクタリング時は既存機能を破壊しない
- 新たなTODOの発見は積極的に記録する

**品質基準:**
- 全てのテストが通る状態を維持
- コードカバレッジを意識したテスト作成
- 単一責任原則を守った実装
- 将来の変更に対する拡張性を考慮

実装を開始する前に、TODO.mdの現在状況を確認してください。
